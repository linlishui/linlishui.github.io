概述#

OpenSpec 是一个面向 AI 编程助手的 SDD（Spec-Driven Development，规格驱动开发）工具。它解决的问题不是“让 AI 更快写代码”，而是让一次需求变更先沉淀为可检查、可追踪、可归档的规格资产，再进入实现。

本文基于本机验证的 OpenSpec CLI 1.11.0（截至 2026-09-01 的最新稳定版），包名为 @fission-ai/openspec。当前默认 schema 是 spec-driven，核心产物链路是：

proposal -> specs -> design -> tasks -> apply -> archive

可以把它理解成一条轻量级需求流水线：

  • proposal.md：为什么做、做什么、影响什么
  • specs/：系统应该表现出什么行为
  • design.md：准备怎么实现，关键技术取舍是什么
  • tasks.md：可执行、可勾选、可验证的任务清单
  • archive：实现完成后，把变更合并回主规格

解决什么问题#

只靠聊天记录驱动 AI 写代码，常见问题是需求散落、上下文漂移、实现和预期不一致。OpenSpec 用仓库内的 openspec/ 目录把需求、规格、设计和任务固定下来，让人和 AI 都围绕同一组文件工作。

初始化后的核心目录如下：

openspec/
  config.yaml
  changes/
    archive/
      2026-09-01-add-dark-mode/
    add-dark-mode/
      .openspec.yaml
      proposal.md
      specs/
        ui-theme/
          spec.md
      design.md
      tasks.md
  specs/
    ui-theme/
      spec.md

其中 openspec/config.yaml 保存项目上下文和 artifact 规则，openspec/changes/ 存放进行中的变更，openspec/specs/ 存放已经生效的主规格，openspec/changes/archive/ 存放带日期前缀的历史变更。

安装与初始化#

OpenSpec 需要 Node.js 20.19.0 或更高版本。

npm install -g @fission-ai/openspec@latest
openspec --version

在项目根目录初始化：

cd your-project
openspec init

如果希望生成的 artifact 使用中文，可以在首次初始化时指定语言：

openspec init --language Chinese

这会把语言要求写入 openspec/config.yaml。结构标题以及 SHALL、MUST 等规范关键词仍需保留英文，避免破坏校验规则。已有项目应直接编辑 config.yaml 的 context，openspec init --language 不会覆盖现有项目约束。

如果要非交互式指定 AI 工具，可以使用 --tools：

openspec init --tools codex
openspec init --tools claude,cursor
openspec init --tools none

--tools all 会尝试为所有支持的工具生成指令文件。团队项目里建议只启用正在使用的工具，避免生成过多无关配置。

需要区分两类命令：openspec ... 在终端执行，/opsx:... 在 AI 编程助手的聊天框中调用。文档统一使用 /opsx:propose 这种规范名称，但不同工具的实际入口不同：Claude Code 常用 /opsx:propose，Cursor 和 GitHub Copilot 常用 /opsx-propose，Codex 使用 skill 形式 $openspec-propose。初始化完成后的提示和自动补全才是当前工具的准确入口。

初始化后，如果升级了 OpenSpec 包，需要在项目内刷新指令文件：

npm install -g @fission-ai/openspec@latest
openspec update

日常工作流程#

完整工作流可以概括为“先对齐，再生成规格，再实现归档”。OpenSpec 默认使用 core profile，包含 explore、propose、apply、update、sync、archive。日常主线如下：

flowchart TD
    A["/opsx:explore
可选：澄清需求"] --> B["/opsx:propose
生成 proposal/specs/design/tasks"]
    B --> C["openspec validate
校验规格"]
    C --> D{校验通过}
    D -- 否 --> E["/opsx:update
修正规划 artifact"]
    E --> C
    D -- 是 --> F["/opsx:apply
按 tasks.md 实现"]
    F --> G{需求或方案有变化}
    G -- 是 --> E
    G -- 否 --> H["/opsx:archive
归档并更新主规格"]

如果团队要求在归档前先评审主规格，可以显式执行 /opsx:sync；多数情况下 /opsx:archive 已经会合并 delta specs。new、continue、ff、verify、bulk-archive 和 onboard 属于扩展工作流，启用方式见后文。

1. 探索问题#

需求还不清楚时，不要直接让 AI 生成代码，可以先进入探索：

/opsx:explore 增加深色模式，要求兼容现有主题配置

这个阶段适合让 AI 读代码、澄清边界、确认影响范围。1.11.0 中，只读探索不需要确认；如果探索过程准备创建或编辑 artifact、代码或其他文件，AI 应先列出目标并在单独一轮中取得明确同意，用户回答澄清问题本身不视为写入授权。

2. 创建变更#

常用快速路径是：

/opsx:propose add-dark-mode

它会创建一个 change，并尝试一次性生成 proposal.md、specs/、design.md、tasks.md。

如果改动比较复杂，可以启用扩展工作流后分阶段推进：

openspec config profile
openspec update

然后在 AI 助手中执行：

/opsx:new add-dark-mode
/opsx:continue add-dark-mode
/opsx:continue add-dark-mode

new 只创建变更骨架，continue 会按 schema 继续补齐下一个 artifact。这样更适合需要人工审阅 proposal、spec，再继续设计和拆任务的场景。不要把扩展命令写进团队指南后却忘记更新 profile 和项目内的指令文件。

3. 查看状态#

openspec status --change add-dark-mode
openspec status --all

典型输出会显示 artifact 完成度：

Change: add-dark-mode
Schema: spec-driven
Progress: 2/4 artifacts complete

[x] proposal
[x] specs
[ ] design
[-] tasks (blocked by: design)

blocked 表示前置 artifact 还没完成。默认 schema 中，tasks 依赖 specs 和 design。

1.11.0 新增的 status --all 可以一次查看所有进行中变更，适合多人并行开发和 CI 仪表盘；配合 --json 可以得到顺序稳定的结构化结果。

4. 校验规格#

实现前至少跑一次校验：

openspec validate add-dark-mode --type change

提交前建议跑全量校验：

openspec validate --all --strict

脚本或 CI 中可以使用 JSON 输出：

openspec validate --all --json --no-interactive

如果仓库规格很多，可以直接调整并发：

openspec validate --all --strict --concurrency 12

还可以检查历史归档是否仍有未完成任务：

openspec validate --archived

--archived 只检查归档目录中的 tasks.md 是否全部勾选，不会重复校验已经合并的 delta specs。

5. 修正规划#

规划阶段或实现过程中发现需求变化时，使用：

/opsx:update add-dark-mode 将主题偏好从 localStorage 改为 Cookie

update 只修订已经存在的规划 artifact，不会创建缺失 artifact，也不会修改代码。它会检查 proposal、specs、design、tasks 之间的连锁影响，并逐个确认写入。规划改完后，再执行 /opsx:apply 让实现追上新规格；如果变化已经改变了原变更的核心意图，应新建 change，而不是无限扩张旧 change。

6. 执行实现#

/opsx:apply add-dark-mode

apply 会读取 tasks.md，按待办任务实现，并在完成后更新复选框。这里有一个关键约束：任务必须使用标准复选框格式，否则进度追踪可能失效。

## 1. Theme Infrastructure

- [ ] 1.1 Create theme context provider
- [ ] 1.2 Add theme persistence in localStorage

## 2. UI Integration

- [ ] 2.1 Add theme toggle button
- [ ] 2.2 Verify initial render follows saved theme

7. 验证与归档#

启用了扩展工作流时，实现后可以先验证：

/opsx:verify add-dark-mode

确认实现、规格、设计和任务状态一致后归档：

/opsx:archive add-dark-mode

也可以使用 CLI 归档：

openspec archive add-dark-mode
openspec archive add-dark-mode --yes

归档会校验变更、合并 delta specs 到 openspec/specs/，并把 change 移动到 openspec/changes/archive/YYYY-MM-DD-<name>/。

如果是纯重构、工具或文档改动，长期不需要 spec delta，推荐在 change 元数据中声明：

schema: spec-driven
skip_specs: true

临时跳过本次归档的 spec 合并仍可使用：

openspec archive update-ci-config --skip-specs

端到端示例#

假设要给系统增加深色模式，最小闭环可以这样走：

/opsx:propose add-dark-mode

生成的 proposal.md 应该聚焦动机和影响：

## Why

Users need a dark theme to reduce eye strain in low-light environments.

## What Changes

- Add a user-facing theme toggle.
- Persist the selected theme locally.
- Apply theme variables during initial render.

## Capabilities

### New Capabilities
- `ui-theme`: Theme selection and persistence behavior

### Modified Capabilities

## Impact

- Frontend theme provider
- Header toolbar
- CSS variables

对应的 delta spec 应该描述行为，而不是实现细节：

## Purpose

Provide user-selectable themes and preserve the preference across sessions.

## ADDED Requirements

### Requirement: Theme selection persists
The system SHALL persist the user's selected theme across browser sessions.

#### Scenario: User selects dark theme
- **WHEN** the user switches from light theme to dark theme
- **THEN** the system applies dark theme styling
- **AND** the selection is restored after page reload

实现前先检查状态和校验：

openspec status --change add-dark-mode
openspec validate add-dark-mode --type change --strict
openspec show add-dark-mode --diff

show --diff 是 1.11.0 新增的评审入口。对于 MODIFIED Requirements，delta 必须重述仍然保留的完整 requirement 和 scenario，普通文本看起来会有大量重复；--diff 会把真正变化的行提取出来，便于在实现前快速审阅。脚本中可以组合 --json --diff。

然后执行：

/opsx:apply add-dark-mode
/opsx:archive add-dark-mode

如果已经启用扩展工作流，可以在归档前增加 /opsx:verify add-dark-mode。这个流程的重点是：spec 写系统行为，design 写技术方案，tasks 写可执行步骤。不要把三者混在一个文件里。

Slash Commands#

下面使用官方规范名称；实际调用形式以 AI 工具生成的 skill 或 command 为准。

命令 Profile 场景
/opsx:explore core 调研和澄清问题；写文件前需明确确认
/opsx:propose <name> core 一次性创建变更并生成主要 artifact
/opsx:apply <name> core 按 tasks.md 实现
/opsx:update <name> core 修订已有规划 artifact，不修改代码
/opsx:sync <name> core 将 delta specs 同步到主 specs
/opsx:archive <name> core 归档完成变更
/opsx:new <name> expanded 创建变更骨架
/opsx:continue <name> expanded 继续补齐下一个 artifact
/opsx:ff <name> expanded 快速生成实现所需的全部 artifact
/opsx:verify <name> expanded 验证实现是否匹配规格
/opsx:bulk-archive expanded 批量归档多个完成变更
/opsx:onboard expanded 引导式学习完整流程

日常最小闭环通常是：

/opsx:propose -> /opsx:apply -> /opsx:archive

复杂需求更适合：

/opsx:explore -> /opsx:new -> /opsx:continue -> /opsx:apply -> /opsx:verify -> /opsx:archive

如果方案变化，随时插入 /opsx:update；artifact 是帮助推进工作的依赖关系，不是只能单向通过的阶段门禁。

配置说明#

全局配置文件可以这样查看：

openspec config path
openspec config list

macOS 和 Linux 默认路径通常是：

~/.config/openspec/config.json

常见配置项：

配置 说明
profile 工作流配置，常见值为 core 或 custom
delivery 指令交付方式，支持 both、skills、commands
workflows custom profile 下启用的 workflow 列表
featureFlags 实验特性开关
telemetry.enabled 匿名使用统计开关；未设置时默认开启
defaultStore 本机没有项目 root 或项目 Store 指针时使用的默认 Store

切换 profile：

openspec config profile
openspec config profile core

直接设置配置：

openspec config set delivery commands
openspec config get delivery
openspec config set telemetry.enabled false
openspec config unset delivery
openspec config reset --all --yes

OpenSpec 会读取环境变量控制部分行为：

export OPENSPEC_TELEMETRY=0
export DO_NOT_TRACK=1
export OPENSPEC_CONCURRENCY=12
export NO_COLOR=1

其中 OPENSPEC_TELEMETRY=0、DO_NOT_TRACK=1 或 CI 环境可以关闭匿名使用统计，并优先于全局配置。关闭 telemetry 也会关闭 openspec update 的版本检查；如果只想跳过更新检查，可以设置 OPENSPEC_NO_UPDATE_CHECK。

项目级配置位于 openspec/config.yaml，与全局 config.json 的职责不同。前者用于 schema、项目背景、artifact 规则和 apply/archive 操作指导，例如：

schema: spec-driven

context: |
  Language: Chinese
  All artifacts must be written in Chinese.
  Keep OpenSpec structural headings and SHALL/MUST keywords in English.  

rules:
  tasks:
    - 每个任务都要写明测试命令或可观察的完成条件

operations:
  apply:
    guidance:
      - 实现后运行项目测试

这些内容会进入 agent 指令，但不是 CLI 能自动证明的校验规则；真正需要强制的约束仍应落到测试、lint 或 CI。

Schema 与模板#

当前内置 schema 可以这样查看：

openspec schemas
openspec schema which spec-driven
openspec templates --schema spec-driven

spec-driven 的 artifact 定义是：

Artifact 生成文件 依赖
proposal proposal.md 无
specs specs/**/*.md proposal
design design.md proposal
tasks tasks.md specs、design

如果团队需要自定义流程，可以 fork 内置 schema：

openspec schema fork spec-driven team-workflow
openspec schema validate team-workflow

schema 命令当前属于实验能力，适合在团队内部统一后再使用。个人项目通常不用改 schema，只需要遵守默认模板即可。

规格写法约束#

OpenSpec 中有两种容易混淆的 spec：

  • openspec/specs/<capability>/spec.md 是当前已经生效的主规格，使用 ## Purpose 和 ## Requirements
  • openspec/changes/<change>/specs/<capability>/spec.md 是本次 change 的 delta spec，使用 ADDED、MODIFIED、REMOVED、RENAMED 描述差异

主规格的基本结构是：

# Data Export Specification

## Purpose

Define the user-visible behavior of data export.

## Requirements

### Requirement: User can export data
The system SHALL allow users to export their data in CSV format.

#### Scenario: Successful export
- **WHEN** user clicks "Export"
- **THEN** system downloads a CSV file

delta spec 根据变更类型使用以下标题：

## ADDED Requirements
## MODIFIED Requirements
## REMOVED Requirements
## RENAMED Requirements

如果 delta 引入全新 capability，应同时提供 ## Purpose，归档时它会成为新主规格的 Purpose。修改既有 capability 时，主规格已经有 Purpose，delta 不负责覆盖它。

每个 requirement 使用三级标题：

### Requirement: User can export data
The system SHALL allow users to export their data in CSV format.

每个 scenario 使用四级标题：

#### Scenario: Successful export
- **WHEN** user clicks "Export"
- **THEN** system downloads a CSV file

需要特别注意：

  • 需求描述优先使用 SHALL 或 MUST，避免模糊的 should、may
  • 每个 requirement 至少要有一个 scenario
  • scenario 必须使用 #### Scenario，不要写成三级标题或普通列表
  • MODIFIED Requirements 必须包含修改后的完整 requirement block
  • REMOVED Requirements 应写清楚删除原因和迁移方式

从 1.11.0 开始，主规格仍保留占位 Purpose 会触发警告，在 --strict 下会导致校验失败。归档前应把 Purpose 写成真实的 capability 说明。

跨仓库规格：Stores（Beta）#

单仓库项目继续使用本地 openspec/ 即可。只有当一个需求横跨多个代码仓库，或平台团队需要集中维护共享契约时，才需要 Store：它是单独存放 OpenSpec 规划资产的 Git 仓库，在本机注册后可以通过 --store <id> 显式访问。

openspec store setup team-context
openspec store list
openspec store doctor team-context
openspec list --store team-context

代码仓库可以在 openspec/config.yaml 中把 Store 声明为只读参考：

schema: spec-driven
references:
  - team-context

引用只为 agent 提供上下文，不会改变当前命令的写入目标；写 Store 必须显式传入 --store，OpenSpec 也不会自动执行 Git clone、pull 或 push。Stores、references、context 和 worksets 在 1.11.0 仍是 Beta，命令和文件格式可能继续变化，不建议把它们作为入门必选项。

团队落地建议#

1. 把 OpenSpec 变更作为 PR 的入口#

一个较稳的 PR 结构是：

代码变更
openspec/changes/<change-name>/
测试结果

评审时先看 proposal.md 和 specs/，确认行为契约没有偏，再看实现是否符合 design.md 和 tasks.md。

2. 给 CI 增加规格校验#

如果项目使用 GitHub Actions，可以增加一个轻量校验：

name: openspec

on:
  pull_request:

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20.19.0"
      - run: npm install -g @fission-ai/openspec@1.11.0
      - run: openspec validate --all --strict --no-interactive
      - run: openspec validate --archived

如果希望总是使用最新版，可以把安装命令改成 @latest；如果团队更看重可复现，建议固定版本。

3. 归档前做三项检查#

归档前至少确认：

  • openspec validate --all --strict 通过
  • tasks.md 中实现任务已经完成
  • specs/ 描述的是用户可观察行为，而不是代码实现细节

归档不是清理文件，而是把变更纳入长期规格。不要把未确认的临时方案归档进主规格。

常见坑#

1. 把实现细节写进 proposal#

proposal.md 主要回答为什么要做、做什么、影响哪些能力。具体技术方案应该放到 design.md。

2. tasks.md 不是标准复选框#

apply 阶段会解析 tasks.md。如果任务不是 - [ ] 格式，就可能无法追踪进度。

3. MODIFIED Requirements 写得太短#

修改已有规格时，如果只写新增的一两句话，归档时可能丢失原有细节。稳妥做法是复制完整 requirement，再写更新后的完整版本。

4. 跳过 validate 直接 archive#

归档会影响主规格。除非非常明确，否则不要使用 --no-validate。长期不包含行为变化的 change 应在 .openspec.yaml 中声明 skip_specs: true；--skip-specs 更适合一次性的显式覆盖，但仍建议保留其他校验。

5. 把规范命令原样用于所有 AI 工具#

/opsx:propose 是文档中的规范名称，不保证是当前工具的实际调用方式。Codex 使用 $openspec-propose 这类 skill 入口，Cursor 等工具可能使用 /opsx-propose。遇到“命令不存在”时，先检查 openspec init 生成的文件和工具自动补全，再运行 openspec update，不要反复在终端执行 slash command。

6. 忽略版本差异#

OpenSpec 仍在快速演进，官方文档、main 分支和本地 CLI 版本可能存在差异。写团队文档时建议标明版本，并以本地命令输出为准：

openspec --version
openspec --help
openspec config list
openspec schemas

小结#

OpenSpec 的价值不在于多生成几份 Markdown，而是让 AI 开发过程有稳定的中间产物：变更动机、行为规格、技术设计和任务清单。小改动可以走 /opsx:propose -> /opsx:apply -> /opsx:archive，方案变化时用 /opsx:update 让规划保持一致；复杂改动再启用 /opsx:new、/opsx:continue 和 /opsx:verify 等扩展工作流。

对团队项目来说，建议把 openspec/changes/ 当成需求评审和实现评审的共同入口，把 openspec/specs/ 当成长期维护的行为契约。这样 AI 不再只跟着聊天上下文走，而是围绕仓库里可审阅、可校验、可归档的规格工作。
